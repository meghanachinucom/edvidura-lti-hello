1. What EdVidura is (as I understand it)

EdVidura is a learning platform that opens inside the customer’s existing LMS (for now: Moodle). Students don’t leave Moodle to use our tools.

Inside Moodle, EdVidura can provide quizzes, AI help, digital manuals, skill checks, reports, and later XR. Every learning action should go through one common activity path so progress and grades stay trackable.

It is meant for two kinds of customers:

  • Normal cloud customers — many organisations share one EdVidura system.
  • Defence / high-security customers (later) — they may get a private offline copy (“enclave”).

We are not rebuilding Moodle. Moodle keeps the courses and the official gradebook. EdVidura adds the smart tools on top.

The big plan talks about many modules (around 38 + programme deliverables). An independent review said the direction is good, but readiness is still early.

How Moodle and EdVidura connect (my understanding)

1
Teacher adds EdVidura as an external tool in Moodle.
2
Student clicks → Moodle sends them to EdVidura with a secure login (LTI 1.3).
3
EdVidura knows who the student is, which course, and which organisation (tenant).
4
Later, after a quiz, EdVidura can send the grade back to Moodle.

3. Customer separation (my understanding)

A tenant = one customer organisation. Getting this wrong means School A could see School B’s data. This decision should be locked before tables multiply.

Option A — One shared database + row rules (RLS) CHOSEN for cloud

All customers share the same tables. The database filters rows by customer ID.

  • Good: cheapest; adding a customer is basically a row; one migration updates everyone
  • Watch outs: every table needs the rule; cache/files/queues must include customer ID; need tests that prove A cannot see B

Option B — Separate schema per customer REJECTED

  • Clearer folders, but messy past a few hundred customers; more ops pain than A, less isolation than D

Option C — Separate database per customer NOT PLANNED

  • Strong separation, but cost grows with every customer. For defence, a full private instance is usually what they want

Option D — Full private copy (enclave) CHOSEN for defence (later)

  • Good: strongest isolation; can run offline
  • Bad: every update ships to each site; needs local AI hardware sized and funded

Hybrid A + D TARGET

  • One codebase, two ways to deploy. Every feature should eventually work for both.

What makes shared-DB separation actually safe (checklist I noted) App DB user must not be a superuser · force row rules · set current customer ID on every request · put row rules on every customer table from day one · put customer ID in cache keys, queues, indexes, file paths · run automated “A must not see B” tests.
One non-negotiable rule (as I understood) Customer identity comes only from a verified LMS registration (issuer + client id + deployment) or a trusted login token. Never from a typed URL, email domain, or course name. Unknown registrations are rejected.

The 11 must-fix blockers (short list)

  • Customer separation not proven
  • Grade source of truth unclear
  • No plan for duplicate / lost events
  • No audit trail for official records
  • Skills registry missing while dependents scheduled
  • Offline promised while AI may still need internet
  • Local AI hardware unsized / unfunded
  • Cross-site learner matching undefined
  • No security-approval authority or plan
  • Second lab planned before first design proven
  • No published, testable interfaces yet
My takeaway Most of these are not “we need more code”. They are “somebody must decide and sign”. Without signed decisions, the overall rating cannot improve much.

5. What to do next (my understanding)

Don’t build everything at once. Build thin vertical slices (one complete learner journey), and aim for both cloud and offline readiness over time so defence doesn’t get postponed forever.

Where we are today

We already have a small starter (“hello”) app that:

  • Connects to Moodle with LTI 1.3
  • Resolves which tenant the launch belongs to
  • Uses Postgres with tenant isolation (RLS) for launch events

That proves the front door works. It is not the full product yet.
