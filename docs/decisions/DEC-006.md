# DEC-006 — Shared DB + RLS multi-tenancy (SaaS / connected pilot)

| Field | Value |
| ----- | ----- |
| Status | **Accepted** |
| Date | 2026-08-13 |
| Relates | LTI Hello spike, Slice 0 contracts |

## Decision

EdVidura **connected / SaaS** deployments use:

1. **One shared Postgres database** with a `tenant_id` column on every tenant-owned table.
2. **PostgreSQL Row Level Security (RLS)** with `FORCE ROW LEVEL SECURITY`, enforced under the non-superuser role `edvidura_app` (`NOSUPERUSER`, `NOBYPASSRLS`).
3. **BYO Moodle (LMS):** institutions run their own Moodle; EdVidura is an **LTI 1.3 external tool**. EdVidura does **not** operate one Moodle container per customer.
4. **Tenant identity** comes only from a verified LTI registration (`iss` + `client_id` + deployment → `lti_platforms.tenant_id`). Never from query params, email domain, or unverified headers.

## Consequences

- Onboarding a school = create `tenants` row + `lti_platforms` row (Admin API / `/onboard`), then register tool URLs in their Moodle.
- New tenant-owned tables must follow [`db/rls_template.sql`](../../db/rls_template.sql).
- App code sets `SET LOCAL app.tenant_id` (see `app.db.with_tenant` / `TenantContext`) before reading/writing tenant data.
- **Enclave / air-gap / DB-per-tenant** is a **separate deployment class** (deferred). Do not redesign SaaS schema around it.

## Explicit non-goals (near term)

- Second Moodle Docker stack in-repo for “multi-tenant demo”
- Schema-per-tenant for SaaS
- Full Moodle plugin as the core product (thin helper plugin later OK)
