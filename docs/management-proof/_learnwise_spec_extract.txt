1. Purpose and how to read this document
This specification lists every feature, capability, integration, and non-functional requirement observed in the LearnWise AI platform, organized so an engineering team can plan a replication. Each feature carries an ID, description, user story, acceptance criteria, build priority, and an evidence tag.
Priority: P0 = required for a credible first release of that product; P1 = needed for parity; P2 = differentiating or recent.
Evidence: Confirmed = seen on a public page, help article, or changelog; Inferred = implied by confirmed behavior; Claim = marketing statement not verified; Roadmap = announced for 2026.
Treat all performance figures (ticket reduction, questions answered, ROI) as vendor claims.
2. Platform overview
LearnWise is a multi-tenant, LLM-agnostic retrieval and agent platform for higher education. It is delivered as four independently licensed products on one administrative console (admin.learnwise.ai) and embeds into the systems a campus already runs rather than operating as a separate destination.

9. Workflow engines
9.1 Flows (rules engine)
One always-on default flow per assistant; custom flows evaluated in priority order.
Triggers: user message (intent or keyword), chat window open, page load, time on page.
Conditions with include and exclude: URL pattern, user role, course ID, external data, date range.
Actions, composable and repeatable: search knowledge, answer with guidelines or custom instructions, hand over to a desk, run a quiz, follow-up prompts.
Inferred: message triggers are LLM-classified; an alternative is embedding similarity against example utterances.
9.2 Help Desks (escalation router)
A desk is a team plus channels, hours, a form schema, and a ticketing binding; at least one channel is mandatory.
The assistant selects the desk from context and flow rules.
Payload: conversation summary, transcript with per-message timestamps, start and end time, user metadata unless hidden, page URL at escalation, form fields mapped to the ticketing system&apos;s real custom fields.
Live-agent handover supported for Salesforce Service Cloud; similar for other live-chat tools is inferred.
9.3 Ops Assistant (tool agent)
Tools map to LMS REST endpoints for reads (courses, users, enrollments, assignments, activity) and writes (dates, enrollments, settings).
Every write requires explicit human approval; permissions come from editable role templates.
Audits apply an uploaded rubric across a course set and return flagged issues by category.
9.4 Grader pipeline (inferred from confirmed behavior)
Ingest submission: text, image including HEIC, audio, or video transcribed.
Condition on rubric rows, instructor notes or voice note, feedback profile, custom instructions, optional course content.
Produce structured per-criterion score and comment plus an overall comment.
Return to the LMS grading UI for editing, section rating, annotation, and approval; log active grading time.
Automated path: LTI Asset Processor on Canvas or submission webhook on Brightspace triggers the pipeline on submit.

14.3 Team and effort
Five to seven engineers (two backend and retrieval, one integrations, one front end, one ML for grading, one platform and security) plus a product manager and a compliance lead. Twelve to eighteen months to parity on the four products, excluding the 400-tool content library, which is a content-operations effort.
14.4 Top risks
LMS API drift and per-institution customizations (Blackboard UEF placement limits and ticketing custom fields are real examples).
Grading accuracy and liability; requires calibration sets per rubric and a hard approval gate.
Compliance lead time blocking sales regardless of feature parity.
Agentic write actions in production LMSs; requires dry-run, approval, and rollback.
Pre-trained tool library and ticketing breadth are moats of effort, not technology.
Role-scoped retrieval bugs leaking faculty content to students; requires tests per role per source.
Multilingual quality and RTL layouts across widget and admin.
Cost control on multi-pass retrieval at campus scale.
Accessibility regressions in embedded contexts.
Single-provider lock-in undermining no-training and residency claims.
